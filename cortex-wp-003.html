AI-Native Hardware Architecture

Hardware-enforced trust, model execution, memory separation and controlled knowledge promotion.

DocumentCORTEX-WP-003
Version0.2 research draft
StatusArchitecture research draft
AudienceHuman and AI researchers
Hardware architecture

Abstract

This paper proposes an AI-native hardware architecture in which immutable trust, protected model execution, volatile reasoning, controlled learning memory and independent security monitoring are separate physical or cryptographic domains. It also records the Cortex model-in-silicon direction: a normal computer accesses a local AI appliance through PCIe/CXL or private Ethernet, while fixed model weights execute inside an attested model-specific fabric.

Design objective: high AI performance must not require surrendering control of boot, memory, credentials, knowledge promotion or audit to the reasoning model itself.

1. Architectural principles

  • Immutable root of trust and measured boot.
  • Foundation model identity bound to a specific signed release.
  • Volatile, session-isolated reasoning memory.
  • Physical or cryptographic separation of candidate and validated knowledge.
  • Signed, replaceable skills rather than permanently fused tools.
  • Independent security and promotion controllers.
  • Complete audit trails, rollback and recovery.

2. Logical hardware stack

Normal computer or local network ↓ PCIe / CXL / private Ethernet Host gateway and policy interface ↓ Independent control & security subsystem ↙ ↓ ↘ Model-specific ECC reasoning Signed skills weight fabric and context and tools ↓ Encrypted candidate knowledge ↓ privileged validation gate Versioned validated knowledge ↓ Append-only audit and rollback

3. Immutable trust foundation

A first-stage security controller verifies boot firmware, runtime components, model identity, skill indexes and validated-knowledge roots before ordinary sessions are enabled. The system produces an attestation report so a host can determine exactly which hardware, model mapping and policy set it is using.

4. Model-specific silicon

The long-term Cortex design follows the model-in-silicon principle demonstrated by highly specialised inference hardware: place fixed model weights beside the arithmetic that consumes them rather than repeatedly transporting every weight from distant memory. Cortex treats the user-visible “chip” as one logical accelerator appliance, which may contain multiple replaceable model-tile boards rather than one monolithic die.

Fixed model weights, tensor schedules and model identity belong in the protected model fabric. Prompts, conversations, reasoning state, skills, credentials, adapters and learned knowledge remain writable because they change during operation.

5. Dynamic memory hierarchy

6. Skills and tool execution

Skills are signed, versioned packages stored outside the fixed model fabric. When the model requests a tool, the control subsystem verifies identity, permissions and policy before executing it inside a sandbox or delegating it to the host. Tool output returns to volatile context, and an audit digest records the interaction.

7. Independent security monitor

The security monitor has its own identity, memory and observation path. It can restrict credentials, network routes, devices and validated knowledge even when the main model requests access. A failed signature, stale firmware counter or policy mismatch places the appliance into a diagnostic and recovery state rather than releasing protected resources.

8. Prototype and full-appliance tracks

The Cortex hardware programme separates a lower-cost trust-and-control prototype from the final model-in-silicon appliance. The prototype tests attestation, signed skills, memory separation, promotion controls and local model emulation. The full appliance requires model-specific silicon, large ECC dynamic memory, high-speed host interfaces and a verified licence for the selected open-weight model.

9. Research questions

  • Can a physically separated promotion controller resist attempts by the main model to alter validated knowledge?
  • What model functions should be fixed in silicon and which must remain software-defined?
  • How should replaceable model tiles preserve attestation and rollback?
  • Can dedicated hardware agents provide the low-latency infrastructure required by WP-004's synthetic Internet?

10. Relationship to WP-004

WP-004 extends this hardware pattern into a contained digital world. Dedicated infrastructure agents may operate network routing, DNS, web services, security, organisations and synthetic users quickly enough to maintain a coherent environment for the AI being evaluated.
